# Lockbot 数据源接入

将用户提供的机器范围、Lockbot 服务与资源配置转成可核验的数据源接入。复用已有监控优先；没有监控时可部署官方 Lockbot telemetry 包。资源申请、排队和指标采集独立，低利用率不代表空闲。

## 先确认输入和现状

从用户提供的配置、已批准连接和实际版本读取：Lockbot canonical origin、目标 bot/UUID、节点与设备列表、当前数据源、允许采集的机器/部署主机、访问方式、网页 origin 和授权模式。只问无法核实的关键缺项。机器连接与资源数据源是两回事；不推断堡垒机支持端口转发或用户已授权配置免密。

生成配置前核对下文的输入格式和部署检查。如需部署或改服务，再读用户对应环境的部署/远程连接指引；不要把某位维护者的私有机器、代理、路径当成通用默认值。只读检查可先进行，用户已经授权的配置工作继续执行，不反复确认同一授权；申请新网络/身份范围等额外工作需明确其必要性。

核对服务实际支持的适配器。现有 Lockbot 仅实现 Prometheus 数据源；普通 HTTP JSON 与其他源可按新协议规划适配，但文档存在不代表旧版控制台已经支持。不要伪造 `type: json`、不存在的配置导入按钮或保存接口。

## 执行接入

1. **已有数据源**：读取经批准的只读示例，核实指标、单位、真实采样时间、节点标签和卡 UUID。测试不能扫描无关内网或猜机器/卡的对应关系。
2. **新采集服务**：从匹配版本的官方 Release 获取 telemetry 产出包及 checksum，确认平台/架构并校验。遵循部署说明检查 Linux/Python、驱动/SMI、端口、systemd 和已有服务。无需 MPI 或维护者私有脚本；多机 SSH 模式需要部署账号的已批准非交互访问，本机采集不需要 SSH。
3. SMI 默认每 180 秒采集，批量采集时错峰。用户刷新只读缓存，不反复执行 SMI。CPU 首次差分可能未知，失败/缺卡不能填零。别因无人占锁就查询未授权机器。
4. 明确每个 bot 节点/卡映射，NODE bot 同样核对其实际多卡。选择独立源认证或事先配置好的短期授权；不要选择自动授权后就宣称签名信任已建立。新增源不能覆盖已有源的签名密钥。
5. 只有在目标服务和用户权限明确时保存 bot 数据源。修改前读取并保留原配置，优先使用正常后台字段/验证流程，不用整份陈旧 bot JSON 覆盖其他字段。没有保存权限就交付配置给管理员，不尝试个人 Key 越权管理。

## 输出可复制结果

使用 `python3 scripts/datasource/generate_config.py --input <私有输入.json> --output-dir <本机交付目录>` 生成现有 Prometheus 适配器配置、节点映射与字段填写表。输入格式见下文；脚本只转换与校验本地配置，不探测网络、不部署、不签发 Key、不自动保存。它不能证明资源映射正确。

输入齐全且用户已授权本地生成时，从仓库根目录直接运行上面的命令。成功退出后再单独检查产物。如果这条生成命令被客户端拒绝，说明配置尚未生成，并给出同一条命令供用户在终端执行。

交付至少包括：

- 数据源类型/模板、真实 endpoint、访问模式、刷新/过期设置和每个节点/卡的对应关系。
- `utilization-config.json`（供程序维护/审核）、可复制的节点映射 JSON及控制台填写表。当前控制台没有整份数据源 JSON 导入，不指导用户把整份对象贴入节点映射。
- 已做的验证：来源版本/checksum、服务状态、认证拒绝/成功、各节点与卡覆盖、真实采样时间；标清未测试项。
- 明确状态：已生成、已验证、已保存、服务运行分别描述。源访问是 best effort；Agent HTTP 成功不代表浏览器 CORS/网络已验证，更不保证每个用户可达。

配置与机器目录交付到用户本机私有目录，不默认提交真实清单到 GitHub。可分享配置不包含签名密钥、源 token、Cookie 或 Lockbot Key；秘密仅引用批准的安全文件。SSH 私钥和登录密码不应发到聊天。保留既有资源授权、状态和用户会话；不要为了指标验收申请/释放真实资源。

## 权限与故障

资源网页、个人 Key、OP Key、后台 JWT 只发给对应 Lockbot，不发给数据源。指标使用源专用只读凭证；自动短期授权由源管理员显式建立信任，最长五分钟。不能把长期网页链接当成长期指标凭证，也不能声称普通 OP 已获得指标或详细备注权限。

Lockbot 服务端可独立于采集网络部署。验证当前浏览器和实际查看者能否直连指标网关，并核对 CORS、HTTPS 和本地网络权限。资源链接、管理页和 Agent API 使用节点级授权。原生个人资源台启用统一指标且网关支持 v2 时，按持有整机或持有卡签发。开始验收前确认网关版本及范围，在源端验证缺少凭证、过期或越界的请求被拒绝。

失败只影响指标展示；记录明确的未知/过期/错误，保留可回退配置，停止有问题的新服务而不影响锁与队列。

## 生成配置的本地输入

输入只含非秘密字段，真实机器目录本身也应留在私有目录。以下为虚构示例，运行前换成已核验值：

```json
{
  "profile": "lockbot-v1",
  "name": "示例指标源",
  "endpoint": "https://metrics.example.invalid",
  "access_mode": "independent",
  "node_mapping": {"node-a": "source-node-a"},
  "device_mapping": {"node-a:dev0": "accelerator-uuid-a"},
  "interval_seconds": 300,
  "stale_seconds": 660
}
```

`profile` 支持 `lockbot-v1` 与 `dcgm`。后者生成当前自定义 Prometheus profile 的常见 DCGM 指标及 MiB 单位，必须通过实际源样本验证；不同驱动/exporter的指标名不一定相同。自定义指标需按控制台高级字段核对，脚本不猜名称。

`access_mode: short_lived` 仅在已安装源端网关并登记该源签名信任后选择。生成器不会建立该信任。「高级配置」里的刷新间隔控制浏览器读取缓存的频率，与硬件采集间隔和最长 300 秒的授权各自独立。数据过期阈值应覆盖正常错峰周期。

已有采集记录可附上可选 `node_metadata`，例如 `{"source-node-a":{"hostname":"host.example.test","ip":"192.0.2.42"}}`。生成器将已提供的字段写入私有 `node-metadata.json`。资源匹配和接入验收继续使用 `node_mapping`、`device_mapping` 和实际指标。地址缺失或变更不影响接入，生成器不解析域名或探测主机。浏览器使用的指标服务 URL 仍填 `endpoint`。

## 实际部署与检查

1. 核对 Release 包 checksum，保留 manifest、安装版本和原配置；不运行未知安装脚本。
2. 在已批准部署路径安装，保留 Prometheus loopback监听，独立网关受限对外；systemd unit复制为 /etc 下普通文件，安装目录在挂载盘时设置 RequiresMountsFor，启用开机启动与Restart。只操作此次所属服务。
3. 多机采集核验账号和known_hosts，SSH非交互失败时报告，不自行改变网络或SSH策略。
4. 独立授权源的可分享配置不带token。自动授权用独立签名密钥和源注册表，按源隔离，不能覆盖或复用另一个信任域的密钥。
5. 检查匿名拒绝、合法范围成功、过期/越界拒绝、真实observed_at、0/缺失/失败/过期，以及全部配置卡。采样周期内检查缓存即可，不重复驱动查询。
6. 使用者浏览器验证CORS和可达性；只测试了Agent/管理员端则明确未验证其他用户。故障不能影响锁和队列。恢复配置不能把已撤销token重新变成有效。

## 后台低利用率观测

在 LockBot 服务进程中将 `LOCKBOT_IDLE_OBSERVATION_CONFIG` 指向管理员提供的本地 JSON。观测任务每约 60 秒从各自配置的 Prometheus 读取一批指标，按实际采样时间累计独占锁的低利用率时长。默认仅观察，候选总数记录在服务日志。

同一个采集源下可以登记多个机器人目标。`nodes` 填采集源上每台整机的完整设备标签，`targets` 填机器人 ID、UUID 和资源节点对应关系。按卡锁使用 `cards` 中明确登记的卡号映射。示例中的地址和 UUID 仅供说明。

```json
{
  "sources": [{
    "endpoint": "https://metrics.example.test",
    "nodes": {"host-a": ["0", "1"]},
    "targets": [{
      "bot_id": 1,
      "bot_uuid": "71318f9b-ba55-4ee9-9d43-06d56c47132e",
      "node": "node-a",
      "source_node": "host-a",
      "cards": {"0": "0", "1": "1"}
    }],
    "threshold_percent": 5,
    "max_sample_age_seconds": 240
  }]
}
```

使用机器人已登记的短期授权网关时，在源配置中设置 `"use_bot_metrics_grant": true`。每个源批次只登记一个机器人，最多 64 个节点。后台按轮次获得短期只读授权，并核对机器人的 UUID、网关地址和节点、卡映射。

需要静态 Bearer 鉴权时，在源配置中用 `token_env` 指定存放指标只读凭证的环境变量名称。采集失败、响应过时、记录缺失或间隔超过新鲜度上限时，该资源的观察窗口重新累计。单次读取设置超时，等待数据源时正常锁操作可以继续。

在某个 `targets` 条目中设置 `"recover_idle": true`，启用该目标的低利用率回收。连续 20 分钟低于阈值且提醒送达后，持有人有 10 分钟可以恢复使用或确认保留。群命令锁的持有人可以发送 `keep node-a` 或 `keep node-a dev0`，确认后再多给 10 分钟。用逗号分隔可确认多个资源，例如 `keep node-a,node-b`。服务在窗口结束后等待一份完整的新样本，再复核同一把锁。设备有缺失、采集失败或数据过期时保留锁，已有排队继续按原规则处理。

机器人编辑页的“20 分钟低利用率检查”开关默认开启，只对已登记后台采样目标的资源生效。关闭后停止观察和回收。

提醒会显示触发阈值以及最近一次采样的利用率。整机锁显示各卡中的最高值。在机器人编辑页开启“Agent 锁定的低利用率提醒发到群里”后，Agent 锁定的资源也会在机器人所在群提醒持有人。持有人可以在群里 @ 机器人发送提醒中的 `keep` 命令，也可以通过 Agent 确认。两个入口共用同一次 10 分钟延长。同一持有人在采样新鲜度允许的间隔内重新锁定同一资源时，连续低利用率和已送达提醒的复查时间会继续累计。恢复使用、换人或采样中断会重新开始观察。

## 交付示例

“已生成节点与设备映射；已验证采集器和网关，实际覆盖2节点8卡；配置尚未保存。浏览器网络与CORS待目标用户验证。签名文件由管理员私下安装，不包含在复制内容中。”

只有真的保存并从相同bot重新读取到一致配置，才把状态改为“已保存”；只有实际运行证据才报告已部署。不要以样例数据、文档检查或单一health 200代替这些结果。
