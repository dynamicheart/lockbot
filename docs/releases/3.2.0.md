# Lockbot 3.2.0 release candidate

This document prepares the next minor release. **3.2.0 has not been tagged, published or deployed. Formal production remains 3.1.0.** Merged source, CI, integration-group acceptance, publication and formal upgrade are separate gates. This version change does not authorize any of those external actions.

## Changes since 3.1.0

- [PR #70](https://github.com/dynamicheart/lockbot/pull/70): add durable, public allocator lifecycle evidence and a frozen bounded OP export. Stable event/holding identities, versions, initiator/correlation metadata and explicit coverage distinguish committed allocations from requests. The original history endpoint/report remains compatible; incomplete, pre-contract and cross-restart intervals remain unknown. See [the lifecycle contract](../design/verified-allocation-history.md).
- [PR #68](https://github.com/dynamicheart/lockbot/pull/68): optionally acknowledge narrowly defined committed Feishu successes with a reaction. Missing permissions or reaction failure fall back without repeating the resource operation. Query, queue, error and reminder behavior retains its existing reply path.
- [PR #71](https://github.com/dynamicheart/lockbot/pull/71): optionally guide newly joined Feishu groups and record trusted membership/removal notices. Group association still requires explicit authorization; a membership event does not expose a resource pool or bind a group automatically.
- [PR #72](https://github.com/dynamicheart/lockbot/pull/72): optionally update an application's own Feishu group query panel in place. Group/application identity, message ownership and conservative fallback preserve isolation; critical resource-operation results and reminders retain normal delivery.
- [PR #74](https://github.com/dynamicheart/lockbot/pull/74): keep metric process details within narrow viewports and make long container information readable. The accepted 390px desktop-browser check used real Vue rendering with fictitious data; it is not physical mobile/touch or hardware acceptance.
- [PR #73](https://github.com/dynamicheart/lockbot/pull/73): add typed, versioned messaging-application credentials with encrypted storage, additive/idempotent legacy backfill and validated backup/restore. Retained adapters/clients revalidate before outbound requests, including after token refresh; expiry, invalid schema, identity changes or credential rotation fail closed. Legitimate Secret rotation refreshes the current client guard. See [credential compatibility and deployment](../design/platform-application-credentials.md).

The Feishu options **default off** for both existing and new bots:

| Setting | Optional behavior |
| --- | --- |
| `FEISHU_REACTION_REPLIES` | Short-success reactions |
| `FEISHU_MEMBERSHIP_NOTICES` | Membership guidance/removal notices |
| `FEISHU_QUERY_PANEL` | In-place full-query panels |

Do not enable them or add platform permissions as an incidental effect of upgrading. Infoflow remains supported. Private chats, cross-platform shared pools and automatic resource reclaim are not introduced.

## Compatibility and data preservation

- The published Agent API version remains **1**. The additive lifecycle export advertises its own V2 contract/capability; it does not replace the existing API, schema-1 history, personal keys, OP keys or separate detailed-note delegation. A public OP lifecycle export contains no Agent labels or detailed notes.
- `platform_applications` is an additive encrypted registry. Valid legacy Infoflow bot columns, Feishu application/route rows, stable bot/application identities, bindings and original keys remain usable through validated compatibility paths. Backfill does not rotate keys/secrets, rewrite unchanged legacy ciphertext or enable optional features. There is no generic unvalidated credential-JSON write endpoint.
- Keep the existing database/state volume, deployment port, `ENCRYPTION_KEY` and JWT configuration. Existing valid bot configuration, ownership, locks, queues and authorizations must survive the upgrade. Lifecycle state gains a bounded outbox/recovery envelope; legacy history is not silently certified as complete. Do not run old/new writers or competing receivers against the same state/application.
- Unsupported, expired or corrupt credential envelopes fail closed; they do not revive an old credential via fallback. Data compatibility does not waive current expiry, identity, disclosure or authorization checks. Finite-expiry receiving/transmission checks cannot recall a platform request already sent or undo an in-flight operation.
- No additional metrics collector, proxy service, network port or enterprise permission grant is required by the credential registry. Existing direct data-source queries and separate metrics trust are unchanged. Optional Feishu permission/publication decisions belong to the authorized enterprise workflow.

Preserve a consistent database/state backup and the original encryption key before deployment. Database readability alone does not prove a safe downgrade: old code may restore older privacy behavior, ignore registry expiry or discard lifecycle metadata. Follow [upgrade/rollback boundaries](../design/upgrade-rollback.md); do not recover by destructively replacing current occupancy or regenerating keys.

## Evidence already recorded

- Each listed feature PR was independently reviewed and passed its required current-head CI before merge. The release-candidate PR needs its **own** checks; earlier green heads cannot substitute.
- Lifecycle smoke on an isolated loopback HTTP service exercised four frames/five pages, mutation/OP denial, same-UUID journal-failure/SIGKILL recovery and stable IDs over two restarts, with unknown cross-restart coverage. Outbound requests were blocked, platform delivery stubbed and Feishu SDK disabled. This is not real integration-group or formal-service acceptance.
- Credential PR #73 passed six checks on `566c289`, 2,061 tests / 7 skipped and 154 independent checks (overlapping evidence, not summed). A read-only formal-data clone preserved 38 bots / 14 bindings across 17 tables / 643 rows: all 38 configurations remained readable, repeat backfill changed zero rows, hashes remained unchanged and unknown schema failed closed. Temporary data was removed and the running container was unchanged. This was a **clone preflight, not a live migration**.
- The seven verified, sanitized [setup-guide screenshots](../usage/feishu-setup.md) document read-only console views. They do not prove a new enterprise application, permission change or approval workflow. [Issue #24](https://github.com/dynamicheart/lockbot/issues/24) is closed after independently reviewed acceptance on one real cooperating Codex parent → subagent → external HTTP run against fictional integration resources (service 3.0.2; no formal upgrade). The successful run used 23 HTTP requests: same-origin Skill/hash verification, command-only final serialization, rejected child policy expansion, owner/foreign-note/revision checks, If-Match cleanup that preserved the lock, stale 412, actor/start-time/expiry-checked release and verified manifest feedback routing. A first over-polling attempt stopped on 429 without mutation replay; its short lease expired and idle was checked before a new run with repeated GETs at least ten seconds apart. This is not automatic installation/update, adoption by arbitrary hosts, a sandbox against a malicious child or atomic compare-and-free. Private runners/raw proof are not included.

## Gates before publication and formal upgrade

- Pass release-candidate current-head tests/build/required CI and review the final diff. Confirm software/package/frontend version 3.2.0 while keeping API version 1.
- Deploy the accepted candidate to the integration service only under its existing authorization. **Real authorized-group acceptance on that service is not complete**: verify lifecycle restart/export/coverage, existing Infoflow and Feishu resource operations, optional panels/membership/reactions and privacy/default-off behavior as applicable. Do not expand corporate-tenant permissions to pass a test; optional test-enterprise permissions need their own explicit approval.
- Separately authorize tag/publication, image/bundle builds and artifact download/checksum verification. This PR creates no tag or GitHub release and performs no deployment.
- Before a later formal upgrade, preserve port/key/configuration/state and repeat migration preflight on an isolated copy. After the authorized upgrade, verify health/versions, original identities/keys/bindings, locks/queues, public/private projections and source queries against the actual running service.
- Record the exact deployed commit/artifacts and real results in [ROADMAP](../../ROADMAP.md) and issues #27/#54/#57/#62/#63/#64. Those acceptance issues are **not all closed** by this candidate or its feature merges. No new formal upgrade, release success, corporate approval, actual card-hours or productive-work claim is made here.
