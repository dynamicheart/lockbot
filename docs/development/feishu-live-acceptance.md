# 飞书候选的真实验收执行单

本执行单供主进程在确认唯一接收端后使用，不是自动发送/部署脚本。没有执行真实请求或发消息。当前候选的源 commit、运行服务 manifest 和当前 head CI 必须一致；只看包版本（可能仍为 2.15.2）不足以区分未发布候选。

## 工具与旧证据的用途

| 工具/证据 | 可证明什么 | 不能替代什么 |
| --- | --- | --- |
| `tests/backend/test_feishu_release_integration.py` | 隔离 API→原生通知→个人/其他用户资源→普通 owner state→OP history 的身份/隐私连接 | 实际飞书平台权限、客户端渲染或网络 |
| ingress / connector / proxy / transport 测试 | 签名、租户/多群、持久去重、单进程连接器复用、SDK 管道、代理参数和结构化 emoji/link/at | 当前运行进程的真实握手、断线恢复与最终投递 |
| PR #23 gallery | 仅 dry-run 即可生成虚构消息目录；显式授权发送后可检查客户端样式 | gallery 非生产 Adapter，也不接收事件，不证明资源操作或当前隐私策略 |
| 早期 query/short-lock/group-reply 记录 | 当时的接收端/平台链路 | 新候选整合后的代码/权限验收 |
| 通知尾部证明 | 记录的旧候选能在无第四次请求时发出尾部通知，并完成隔离资源清理 | 新候选的全部 Feishu 私密历史权限与多群视觉测试 |
| 正式 v2.15.2 升级证明 | 正式的隐私/通知维护版及指标可用性 | 正式服务没有飞书；不能拿它证明飞书已经上线 |

旧证据保留在任务私有输出目录，不将其原始地址、群/用户标识、凭据、截图里的私密字段或部署路径复制到 Issue。公开状态仅记录已脱敏的 commit、版本、结果和限制。

PR #23 尚未合入时，先在审核过的 gallery checkout 执行默认 dry-run，并使用当前候选的核心包。不要加 `--send` 或私有 target-file，也不要启动接收端：

```sh
PYTHONPATH=<candidate-checkout>/python python3 \
  <reviewed-gallery-checkout>/scripts/dev/feishu_message_gallery.py \
  --report <private-output>/gallery-dry-run.json
```

这是占位路径，需由操作者选择。dry-run 通过不计为真实平台验收。生产 Adapter 的隔离测试仍是本候选的主要格式回归。

## 执行顺序与最小证据

1. **接收端与版本。** 主进程先确认同一企业应用只有一个被选定的接收端，停止旧的本地/远端候选后再切换。记录候选源 commit、manifest/包版本、安装的固定 SDK/依赖及当前 CI run；不记 secret、连接票据或原始 WebSocket URL。进程存在不等于握手完成。
2. **配置保护。** 记录现有如流配置、授权与资源状态已保留；只选择已授权测试应用/群和专用虚构资源。确认 bot 已加入群、成员在应用可用范围、企业发布完成。群名查找成功不能代替这些检查。
3. **真人事件与路由。** 在两个明确授权的资源群分别真实 @ 当前 bot 查询，记录各自的响应目标与对应资源集合。普通文字、单聊、对另一个 bot 的提及不应执行业务，也不应因单聊产生帮助回复。无第二个授权群时，真实多群项目标为未验证，不能用 mock 冒充。
4. **短锁/排队。** 仅在专用虚构资源申请短租约；查询真实 actor、资源、start_time/expiry 确认获得。排队请求不是已经获得资源。需要第二个人时必须使用第二个真实已核验身份；共用个人 key 的多个 Agent 不是两个用户，不伪造平台用户 ID。
5. **消息格式。** 分别检查查询、申请、排队、到期/可用提醒、Agent 绑定说明及网页链接。记录 emoji、空行、可点击 URL、真实 @用户/@全体与长回复的客户端视觉结果。仅在已授权目标和已审内容下发送；平台 accepted 不代表用户已读。没有验证某种客户端/窄屏则明确 unknown。
6. **当前隐私。** 用既有已核验凭证检查同一人的个人视图可读自己的私密备注，其他用户/共享页面/普通 owner/普通 OP 不可读。super-admin 私密读单独检查；请求新权限或新凭证不应作为普通 OP 的回退。历史搜索/分页/下载也要覆盖，不在群里发送私密备注原文或把它保存为公开证据。没有实际第二人时单独标明，而非把普通 owner 当成第二个 IM 用户。
7. **通知与业务来源。** 检查短 burst 无第四次触发也有尾部资源通知，公开分类可见、自由备注和 Agent 名不可见；监控区分真实群事件和个人 API 操作，不因通知计数再增加一次资源命令。这里只报告操作/结果，不推算占用小时或硬件利用率。
8. **冷启动/恢复。** 只由主进程安排受控停止/重连，观察实际新握手后再发一次明确短查询；确认没有旧接收端竞争。姓名/群名冷缓存无权限时应安全回退，权限失败不得变成身份合并。断线时结果不明的命令不能自动重放，先读状态。
9. **清理。** 根据真实 actor、专用资源及租约 start_time/holding evidence 只释放本次已核验租约，清理本次预约/声明，恢复本轮临时覆盖；不用裸 `free`，不做全 bot 强踢，不撤销用户希望保留的 key。记录原有如流资源和授权未变。不要把清理误当成撤回已经发出的历史消息。

## 证据记录约定

一轮记录至少包含：candidate commit、运行 manifest 验证状态、唯一 receiver 确认、每个测试目标的脱敏标签、各步骤 `pass/fail/pending/unknown`、平台接受与人工视觉确认的区别、作用域/租约独立读取、清理结果、保留配置的结果及未完成项目。源码单测、真实平台、正式发布分别记录，不复用一个笼统的“测试通过”。

结果不明时保留 unknown，不自动重试发送、重绑凭据或续锁。公开 PR/Issue 只汇总安全事实；详细 message ID、真实身份、内部 URL 和原始返回值仍留在私有证据中。只有上述必需门槛确认后，才由主进程决定将草稿转为 ready；CI 绿灯本身不授权合入或升级。
