# 按卡排队机器人 QUEUE_DEVICE

QUEUE_DEVICE 用于一台机器有多张卡、需要分别排队的场景。它沿用 DEVICE 的机器和卡号配置、QUEUE 的先到先得规则。已有 NODE、DEVICE、QUEUE 机器人不会自动转换，原有命令和个人 key 的范围保持不变。

## 使用流程

例如 node1 有两张卡：Alice 的开发 Agent 用 `lock node1 dev0 2h` 申请卡 0，她的测试 Agent 可用同一个个人 key 申请卡 1，并给两次请求设置不同的 Agent 名称和用途。两个任务各自记录，不会覆盖彼此。

Bob 用 `book node1 dev0 30m` 加入卡 0 的队列。卡 1 的占用和队列不受影响。轮到 Bob 时，机器人在群内提醒；Agent 继续读取资源状态，在 5 分钟领取窗口内调用该卡返回的 `claim_command`，例如 `lock node1 dev0`。未指定时长时沿用预约时长；确认本人已持有后才开始工作。只预约不代表已取得卡。

`free node1 dev0` 取消本人的该卡预约或释放该卡的锁。`dev0,2` 和 `dev0-3` 可选多张卡；不写卡号会选择对应机器的全部卡，裸 `free` 仍会释放该用户在这个 bot 下的所有持有和预约。多个 Agent 共用 key 时应使用明确卡号，避免影响同一用户的其它任务。

多卡申请整体校验，任一目标不可申请时不修改其它目标。每张卡仍有独立队列，跨卡同时领取可能需要等待所有目标都轮到自己；Agent 应优先按状态中每张卡的领取命令操作。共享锁 `slock` 不支持。人类群命令的抢占和管理命令沿用原有权限，个人 Agent API 继续禁止 `take`、`kickout` 和 `kicklock`。

## API 与用途

资源查询仍返回机器列表，在 `resources[].devices[]` 中增加每张卡的队列、本人位置、可领取标志和领取命令。调用者自己的下次事件时间会包含卡级锁到期和领取截止时间。Agent 不需要猜测语法：读取 bot 类型、`supported_operations`、`command_examples` 和卡上的 `claim_command`。

每张卡有稳定的用途资源编号，例如 `node1:dev0`。这个编号用于结构化用途接口和 OP 资源选择，群命令继续使用 `node1 dev0` 的原有语法，不修改原始 lock 正则。API 的 `lock`、`book` JSON 可以同时携带 `agent_label` 和 `purpose`，成功后直接登记，不需要再调用一次用途 API。

用途表仍按 bot、个人授权和资源编号唯一关联，用持有/预约的实例证明防止旧任务串到新锁上。排队通知保留原预约标识，领取后可继承任务。释放、取消、过期、抢占或撤销授权后，读接口立即不再返回失效用途，后台清理删除失效行。操作历史保留在轮转日志文件中，不随实时用途清理删除。

普通 DEVICE 的用途仍按机器登记，避免改变已发布接口语义；需要同机不同卡独立任务时选择 QUEUE_DEVICE。

## 网页与运维

后台和只读网页按卡显示占用人、完整预约队列和时间，沿用 Lockbot 表格与手机样式；用途在悬停、聚焦或点按时查看。Agent 名称是任务自述，不是鉴权身份。

OP 快照包含每张卡的持有、排队和用途。`opkick` 沿用机器加 `dev` 卡号列表，可释放指定用户的指定卡。`kicklock` 使用返回的卡资源编号，例如 `node_keys: ["node1:dev0"]`，释放该卡当前持有而保留预约；不会隐式把一个裸机器 ID 展开为全部卡。所有目标先验证，未知卡不会造成部分释放。个人 key 不能调用这些运维接口。

## 存储、升级与回退

不新增数据库表或修改已有字段。卡状态继续保存在每个 bot 的 `bot_state.json` 中，机器对应卡数组，每张卡增加 `booking_list`。用途复用现有表，卡编号作为 resource_id。旧类型的存储布局不变。

升级不会转换现有机器人。回退到尚不认识 QUEUE_DEVICE 的版本前，应先停止这类新机器人；旧代码仍可运行原有三类机器人，但无法使用新类型。不要把新类型状态文件当成 NODE/QUEUE 文件，也不要为了回退覆盖全平台数据库或清空已有资源状态。

本阶段增加卡级排队，不引入 Agent 间消息系统、回调地址或另一套凭据。协作仍通过受权限保护的资源状态、用途和队列完成。
