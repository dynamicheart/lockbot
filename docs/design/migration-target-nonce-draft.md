# Migration target delivery proof (disabled management workflow)

This draft replaces a mandatory own-membership API dependency with a fresh group-delivery proof using already approved events. The read-only test application returned HTTP 400 / code 99991672 for the own-membership API under its seven published baseline scopes; no extra member-list or enterprise-admin permission is requested here.

The private creation function requires a current super administrator with unchanged session version and no pending password change. The administrator explicitly attests reviewed publication/usable-range evidence for the exact target digest, recording an opaque evidence reference and a validity bound of at most one hour. This is an administrator review, not an automated provider approval verdict. Creation has no management HTTP route and migration execution remains disabled.

The server creates a 256-bit random nonce with a two-minute lifetime. Only its digest is stored, scoped to service instance, operation, unchanged source digest/revision/owner and exact target application fingerprint/tenant/group. A verified bot-added observation must already exist. Each operation can create at most 32 receipts; proof ingress has separate bounded application/actor budgets.

An administrator sends the returned `migration-check ...` command with an actual @mention of the exact bot in the destination group. The existing receiver must first verify the event's transport and normalize the real group sender/mention. The private official-SDK pipe may establish that trust boundary; HTTP proof consumption requires the existing encrypted-envelope/raw-body signature verification. Plain token-only HTTP and direct unverified internal calls cannot consume a proof, while their existing ordinary command behavior is unchanged.

The proof processor runs before resource routing, allocation, unbound hints or public command logging. It never binds a group, creates a resource bot, sends a message or changes source allocations. It requires a post-creation provider timestamp, exact app/tenant/chat and still-current source/target/reviewer scope. A conditional pending-to-consumed update makes the receipt one-use. Replays and failures return only a generic acknowledgement; nonce plaintext, raw text, source keys and task details are not persisted. The event reference is stored only as a digest.

A receipt proves that a fresh addressed group event reached this receiver and that an administrator reviewed publication evidence. It does **not** prove the sender controls an Infoflow account, establish resource ownership, transfer personal keys or authorize a cutover. Inspection still returns `can_commit: false` and `account_ownership_verified: false`. Current scope, reviewer session and expiry are checked again on inspection. A metrics drain can outlast this two-minute proof: request fresh proof while checkpointed rather than extending its lifetime or extending user leases.

Pending/consumed receipts are private migration evidence under the journal's retention policy. Source/destination principal linking and current declaration ownership require a separate source-key-authenticated pairing workflow with exact signed target actors, explicit administrator mapping review and re-enrollment. The active-state planner remains disconnected from execution. Before enabling management endpoints, independently review proof retention, confirmation UX, current authority checks and remaining fault/backup/active-state acceptance gates.

Tests use fictional local data and no provider requests. They include the existing real HTTP encryption/signature gate (invalid signature rejected before consumption), official-SDK entry, actual own-mention normalization, scope/session revocation, one-use replay and no allocator/route side effects. They do not constitute real enterprise-group acceptance.
