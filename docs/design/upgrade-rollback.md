# 升级与回退

本文针对从没有 Agent 功能的 2.9.5 升级到 2.10，以及上线异常时回退。正常运行时不需要执行回退。

## 上线前保留什么

停止旧服务后，保存旧版本程序、数据库和资源状态目录的一致备份，并保留原加密密钥、部署配置及 DATA_DIR。不要只复制运行中的 SQLite 主文件而遗漏尚未合并的 WAL，也不要让两个版本同时写同一份数据。

升级增加 Agent 相关表和 bot 配置字段，保留原有资源状态结构。旧数据库首次增加“允许 Agent 访问”“群内操作通知”字段时，两者默认开启；已经存在且明确关闭的设置不会被覆盖。平台推广链接是另一个设置，默认关闭。

## 出现问题时

1. 停止新版本，另存故障现场的数据库、资源状态和日志。
2. 启动保留的旧版本，使用同一 DATA_DIR 和原加密密钥。不要同时运行两个版本。
3. 检查机器人配置、现有占用、预约和群命令，确认可以正常读写。
4. 如果当前数据无法正常使用，再决定是否恢复上线前的一致备份。恢复备份会丢失备份之后的变更，先核对这些变更，不自动覆盖。

旧版本不提供 Agent API，新增加的表可以保留，无需为了回退删除它们。原有群操作应继续使用原来的数据。

## 已验证的边界

在隔离数据上，以 GitHub 的 2.9.5 代码验证了“旧版建库 → 新版升级 → 旧版继续读写 → 新版再次读取”，并验证新版本新建数据库后旧版仍能新增机器人。占用和预约保持一致，数据库完整性检查通过。新字段同时具有数据库默认值，避免旧代码插入机器人时因缺少字段失败。

这不等于所有历史部署和自定义路径都已验证。上线前仍需备份，并核实实际 DATA_DIR、密钥和服务启动配置。

如果回退期间修改过机器人身份或授权相关配置，再次升级时应先暂停相关 bot 的 Agent 访问，核对旧授权是否仍适用，必要时重新绑定；旧版不会维护新增的授权身份版本。不要直接认定所有旧 key 都应重新激活。


群广播新增的三张表不会改变旧版资源表。旧版不会执行广播任务；如果新版本尚有待发送任务，
回退后再次升级时需注意这些任务会继续执行。发送结果不确定的目标不会自动重发。

## 旧状态文件兼容

启动时，在取得数据目录归属锁、恢复机器人和启动定时任务之前，自动将同一机器人目录中唯一的
`cluster_status.json` 迁移为 `bot_state.json`，保持文件内容与权限。所有机器人均检查通过后才迁移。
如果新旧文件同时存在、发现其他历史数据目录、文件不可读或内容不是可识别的旧状态格式，保留原文件并报错，
不覆盖现有状态。`python -m lockbot.backend.app.state_migration` 仍只读盘点，不执行迁移。

官方 Docker 镜像默认 `DATA_DIR=/data`，沿用 `-v lockbot-data:/data` 的挂载方式。
显式设置其他 `DATA_DIR` 的自定义部署继续按其配置运行。
